# How it works

For anyone who wants to understand the internals or contribute to them. If you
only want to run the thing, [docs/installation.md](installation.md) is the
document you want.

The reasoning behind each design choice lives in
[`docs/design/`](design/) — those are records written before and during the
build, and they are linked from each section below. Where a design record and
the code disagree, **the code is right**; the records are kept because the
reasoning is the expensive part.

## The shape of the thing

One Python service. Two HTTP surfaces, one resolver, one worker, one SQLite
store.

```
src/svtplay_arr/
  models.py       Frozen dataclasses shared by every layer. Depends on nothing.
  naming.py       Release title / filename generation. Depends on nothing.
  config.py       Settings + the settings writer + the field table
  yamlio.py       Atomic YAML write, backup, mtime conflict detection
  store.py        SQLite job store
  mappings.py     The TVDB -> SVT table, its writer, live reload
  discovery.py    Which mappings may be written unconfirmed, + the CLI
  sonarr.py       Sonarr API client (the metadata oracle)
  svt/
    parser.py     Show-page parsing
    client.py     GraphQL search, episode listing, quality resolution
  matching.py     The one episode-matching rule, shared
  resolver.py     The confidence gate
  downloader.py   Downloader protocol + the svtplay-dl implementation
  worker.py       Job execution, atomic publish
  api/
    newznab.py    The fake indexer
    sab.py        The fake download client
    config_ui.py  The configuration page
  app.py          Composition root, /health
```

The seams are the design, and they are worth stating as rules:

- **Only `resolver.py` makes matching decisions.** The API modules translate
  wire formats; they do not decide.
- **Only `svt/client.py` knows SVT exists.** An SVT API change should touch
  that file and nothing else.
- **`config_ui.py` contains no matching logic and no SVT knowledge.** It calls
  the same clients `discovery.py` does. That seam is what makes it impossible
  for a UI change to alter what gets grabbed.
- **Only `matching.py` holds the episode-matching rule.** `resolver.py` and
  `discovery.py` both import it and neither restates it, because the sweep
  decides whether a *series* mapping is safe by counting how often that exact
  rule holds — and a sweep corroborating under a looser rule than the resolver
  later matches under would write mappings the resolver then refuses.
- **Only `discovery.py` decides that a mapping may be written unconfirmed.**
  It mirrors `resolver.py` one level up — refuse on any doubt — and it is the
  only place that rule lives. It decides on **episodes**, not on titles; the
  title is only the search query. Its normalisation survives for ranking and
  deduplication, and is asymmetric on purpose: the trailing-year strip applies
  to Sonarr's title and not to SVT's name.
- **`app.py` only assembles.** If you find yourself adding matching, download
  or wire-format logic there, it belongs somewhere else.

See [`2026-08-24-svtplay-arr-build-notes.md`](design/2026-08-24-svtplay-arr-build-notes.md)
for the full module map and what each one is allowed to know.

## The request flow

From Sonarr deciding it wants an episode to a file appearing in the library.

### 1. Sonarr searches

```
GET /api/?t=tvsearch&tvdbid=288649&season=15&ep=3
```

`api/newznab.py` handles it. It calls `Resolver.resolve(tvdb_id, season, ep)`
and gets back either one `Release` or `None`, then shapes that into a Newznab
RSS channel with one `<item>` or zero.

The `<link>` on the item — the URL Sonarr will fetch the `.nzb` from — is built
from `request.base_url`, the host Sonarr just reached the service on. Never
from configuration. That is a deliberate fix for a bug where a configured host
(`0.0.0.0`, copied from a deployment doc) resolved on Sonarr's side to its own
loopback with nothing listening: every grab died at the `.nzb` fetch, with
nothing in the service's logs, because the request never arrived. Deriving it
from the incoming request makes it reachable by construction.

If anything raises, the search returns an empty channel. Never an HTTP 500 —
a 500 can make Sonarr disable the indexer entirely, whereas "nothing found" is
a state Sonarr already handles.

### 2. The resolver decides

Covered in detail [below](#the-resolver). It returns one `Release` or nothing.

A `Release` carries a GUID, a title, the SVT video id, a quality label, an
estimated size, and a publication date. The title is generated by
`naming.release_title()` and is simultaneously the release title Sonarr sees
**and** the filename the worker will write, because with `renameEpisodes`
disabled those two strings must not be allowed to diverge.

The GUID is `sha1(svt_id, quality)`, stable across searches. That is
load-bearing: on a failed grab Sonarr blocklists the GUID and re-searches. If
the GUID changed between searches, the blocklist would never match and you
would get an infinite grab → fail → regrab loop.

### 3. Sonarr grabs

```
GET /api/nzb/{guid}?svt_id=...&stem=...&quality=...&size=...
```

The response is a small, well-formed NZB XML document carrying the SVT id,
the filename stem, the quality label and the size in its `<head>` `<meta>`
block. It is not a real usenet NZB — there are no segments — but it must be
valid NZB XML, because Sonarr writes it to disk and hands it to the download
client rather than treating it as an opaque blob.

### 4. Sonarr hands it to the download client

```
POST /sabnzbd/api?mode=addfile   (multipart, the .nzb as `name`)
```

`api/sab.py` parses the upload with `defusedxml` (it arrives over HTTP, so it
must not be vulnerable to entity-expansion attacks), reads the meta block, and
creates a row in the SQLite job store with status `Queued`. It answers with
`{"status": true, "nzo_ids": ["..."]}`.

The upload is capped at 64 KB. A malformed, hostile or oversized upload is
rejected with `{"status": false, "error": ...}` — never a 500.

### 5. The worker downloads

`worker.py` polls the store every couple of seconds for `Queued` jobs and
dispatches each one, bounded by an `asyncio.Semaphore` sized to
`max_concurrent_downloads`.

Each job gets its own staging directory, `incomplete/<nzo_id>/`.
`SvtplayDlDownloader` runs `svtplay-dl`'s `get_media()` on a worker thread via
`asyncio.to_thread`, so the event loop — and therefore the queue endpoint
Sonarr is polling — stays responsive.

`svtplay-dl` exposes no progress callback, so a concurrent poller sums the
sizes of the files currently in the staging directory and reports that as
bytes downloaded. It writes intermediate files and then remuxes to the final
`.mkv`, deleting the originals, so summing what is on disk is the right
measure.

Progress reporting is deliberately unable to fail the download: a store error
in the progress callback is logged and swallowed. A monitoring mechanism must
never be able to kill the thing it monitors.

### 6. Sonarr watches

```
GET /sabnzbd/api?mode=queue
```

Real percentages, from real bytes on disk against the size declared in the
`.nzb`. Clamped to 100, because during the remux step both the intermediate
file and the resulting `.mkv` exist at once and the sum can exceed the
advertised size.

### 7. The publish

Covered [below](#the-atomic-publish). One atomic rename.

### 8. Sonarr imports

```
GET /sabnzbd/api?mode=history
```

The finished job reports `Completed` with a `storage` path. Sonarr maps that
path through its remote path mapping, finds the file, and imports it — the same
completed-download handling it uses for any usenet download.

A failed job reports `Failed` with a `fail_message`, which is what
`autoRedownloadFailed` acts on to trigger a re-search.

## The resolver

[`src/svtplay_arr/resolver.py`](../src/svtplay_arr/resolver.py). The only
module in the project that makes matching decisions, and the one to read first.

Design record:
[`2026-08-24-svtplay-arr-design.md` § The Resolver](design/2026-08-24-svtplay-arr-design.md).

### Sonarr is the metadata oracle

The resolver asks **Sonarr**, not TVDB, what a given
`(tvdb_id, season, episode)` is. Sonarr's episode records carry the air dates,
titles and numbering that the import will actually be filed under. Querying
TVDB directly would introduce a second source of truth that can disagree with
the one that matters, and would need an API key the service otherwise does not
require.

### The two-signal gate

The rule below lives in
[`src/svtplay_arr/matching.py`](../src/svtplay_arr/matching.py) as
`episode_matches`, in exactly one copy. `resolver.py` calls it forwards (to
answer a Sonarr search) and backwards (for the RSS feed's reverse rule), and
`discovery.py` calls it repeatedly to decide whether a whole series mapping may
be written with nobody confirming it. Those callers are pinned as holding the
same function object, as actually calling it, and as doing none of the
air-date arithmetic themselves.

Given a mapped series and a target episode, an SVT episode is a candidate only
if **all** of these hold:

0. **It is available.** SVT flags not-yet-released episodes with a non-null
   `upcomingOverlay`. Offering one is a guaranteed failed grab, and because the
   GUID is stable, that episode stays blocklisted when it really airs. The
   reliable signal is the overlay being non-null — never its text. On the show
   this was built against, 14 teasers carried an overlay and only 13 of them
   said "Kommer"; the 14th was the *next* episode, the one a weekly grab asks
   for.
1. **Air date agreement.** SVT's publication date is within
   `air_date_tolerance_days` (default ±1) of Sonarr's air date for the episode.
2. **Ordinal agreement.** SVT's own position within its run equals Sonarr's
   episode number.

**Never SVT's season number.** SVT labelled a run "Säsong 14" that TVDB and
Sonarr call season 15. Mapping is series-level; within a series, episodes are
identified by ordinal plus date only. This is the first commandment of the
module.

Neither signal works alone: two episodes of the worked example share an air
date, so date alone is ambiguous, and SVT's season labelling makes any rule
that reads it walk straight into the trap.

### Exactly when `resolve()` returns nothing

All of these produce `None` and leave the episode Wanted. Each one logs its
reason.

| Condition | Log line |
| --- | --- |
| No mapping row for that `tvdb_id` | `no mapping for tvdb ...` |
| Sonarr has no series with that TVDB id | `sonarr has no series for tvdb ...` |
| The Sonarr API call failed | `sonarr lookup failed for tvdb ...` |
| Sonarr has no such `(season, episode)` | `sonarr has no episode S..E.. ...` |
| Sonarr's episode has no confirmed air date | `... has no confirmed air date yet` |
| Fetching SVT's episode list failed | `svt episode list failed for slug ...` |
| **Zero** candidates passed the gate | `N candidates, refusing to guess` |
| **More than one** candidate passed the gate | `N candidates, refusing to guess` |
| Quality resolution against SVT failed | `quality resolution failed for svt_id ...` |
| SVT offered no resolvable quality | `no resolvable quality for svt_id ...` |

Two candidates is not a tie to be broken by preference. It is ambiguity, and
ambiguity is failure.

The reason for all this strictness is one line of Sonarr configuration:
`renameEpisodes` is off, so the release title becomes the permanent filename in
the library, and a wrong match is not something a retry fixes. Some episodes
needing manual intervention is the accepted cost.

### Quality is resolved, never assumed

The quality label in the release title is queried from SVT at search time, by
fetching the video endpoint and reading the HLS master playlist it points at
(`RESOLUTION=` and `AVERAGE-BANDWIDTH=` on the `#EXT-X-STREAM-INF` lines).
Quality is not in the video endpoint itself, despite appearances.

If the indexer advertised a quality the download would not deliver, that lie
would be baked into the library — because the release title is the filename.

### The reverse rule, for the RSS feed

`Resolver.recent()` backs a bare `t=tvsearch` with no parameters, which is both
Sonarr's save-time indexer test and its RSS sync. It cannot use the forward
rule directly, because there is no `(season, episode)` to start from.

So it walks the match backwards: for each mapped series, take SVT episodes that
are available, have an ordinal and a publication date, and fall inside
`rss_window_days`. For each, find Sonarr episodes where the season is greater
than zero and `matching.episode_matches` holds — the same predicate as the
forward rule, read from the other end, so the two cannot drift.
**Exactly one** match, or the candidate is skipped.

Season 0 is excluded deliberately: a special dated alongside the run would
satisfy both signals and claim the episode, writing a permanent `S00Exx`
filename for something that is really `S15Exx`.

Having found the `(season, episode)`, it then runs the **forward** rule to
produce the release, so a release from the RSS feed is byte-identical to one
from a targeted search. It also asserts that the forward rule came back with
the SVT id it started from, which catches page drift between the two calls.

The whole sweep memoises Sonarr's series and episode lists and SVT's show page,
because a full `resolve()` per candidate would re-fetch a 171 KB page every
time — traffic that starts to look like scraping as the window widens. The
memo is per-sweep and thrown away, because SVT's availability data is the one
thing that must never go stale.

One broken mapping does not empty the feed: failures are caught per mapping
*and* per candidate. An empty feed is what makes Sonarr reject the indexer.

## The mapping table

[`src/svtplay_arr/mappings.py`](../src/svtplay_arr/mappings.py).

`MappingTable.load()` is strict on purpose. A file that is empty, is not a
top-level mapping, has no `series` key, has a `series` that is not a list, or
contains two rows sharing a `tvdb_id` — all **raise**, rather than returning an
empty table.

That distinction matters because "no mappings" and "the file is broken" used to
look identical to the caller, so a broken file was installed over the working
table without a word in the log. `series: []` is the one legitimate way to hold
zero mappings, and that loads successfully.

### Live reload with last-known-good fallback

`ReloadingMappingTable` wraps the same two-method interface (`for_tvdb`,
`all`) and re-reads when the file's mtime changes. Mappings are the one thing
the configuration page changes often, so requiring a restart to add a show
would remove most of the point of having a page.

**Its failure mode is load-bearing.** On any load failure — unreadable,
unparseable, or an unrecognised top-level shape — it keeps serving the last
table that loaded successfully and logs a warning. It must never return empty
because of a parse error: an empty feed is what makes Sonarr reject the
indexer, a defect this project shipped once already.

Two failures are tracked separately, because they clear differently. A file
that was reached but would not load stays failed until the file changes. A file
that could not be reached at all (deleted, or a permissions change on the
directory above it) clears the moment a `stat` succeeds, even with the file
byte-identical — nothing about the file was ever wrong. Collapsing the two into
one flag left a cleared permissions problem reporting degraded forever, and a
`/health` that cries wolf is worth no more than the silent one it replaced.

`status()` is what `/health` renders: `ever_loaded`, `degraded`, `count`. See
[docs/configuration.md](configuration.md#what-happens-when-it-is-invalid) for
how to read the combinations.

Design record:
[`2026-08-25-config-ui-design.md` § Reload model](design/2026-08-25-config-ui-design.md).

## The wire surfaces

Both modules translate; neither decides anything.

### Newznab — [`api/newznab.py`](../src/svtplay_arr/api/newznab.py)

Newznab is the protocol usenet indexers speak: an HTTP endpoint answering
`?t=<function>` with RSS/XML. Sonarr is a client of it.

**What is implemented:**

| Request | Behaviour |
| --- | --- |
| `t=caps` | The capabilities document. Static. |
| `t=tvsearch` with `tvdbid`, `season` and `ep` | A targeted search. Zero or one `<item>`. |
| `t=tvsearch` or `t=search` with `q` | The recent-releases feed, filtered to the series whose mapped `series_title` contains `q`, case-insensitively. |
| `t=tvsearch` or `t=search` with neither | The recent-releases feed, capped at 100 items. |
| Any other `t` | An empty channel. |
| `GET /api/nzb/{guid}?...` | The synthetic `.nzb`. |

**About `q`.** Sonarr never sends it — it searches by TVDB id — but the
capabilities document advertises it, and Prowlarr and hand-rolled clients do
send it, so it is implemented. Three things about it are deliberate:

- **It filters, it does not match.** Every release it can return has already
  come back from `Resolver`, so a query can only remove items from a feed. It
  can never introduce a release, and it can never produce a title (and
  therefore a filename) that a targeted search would not have produced.
- **`tvdbid` wins.** A search carrying `tvdbid`, `season` and `ep` answers from
  the id alone and ignores `q`. Sonarr sends the series' *English* title in `q`
  while the mapping table holds SVT's Swedish one; filtering an exact answer by
  that guess would drop correct grabs.
- **A blank `q` is no query at all.** Clients send a bare `&q=` on an
  unfiltered search. Reading that as a filter would empty the channel, and an
  empty channel is what makes Sonarr reject the indexer.

The query is matched against the mapping table's `series_title`, not against
the release title: a release title is also a filename, so characters like `?`
are stripped from it, and an operator searching for `Vem vet mest?` — the
spelling the config page shows them — would otherwise find nothing.

**What is not:** movie search is advertised as `available="no"`, and nothing
answers it.

**Two things in the caps document are load-bearing:**

- `supportedParams` on `tv-search` **must** include `tvdbid`. Without it Sonarr
  falls back to `q,rid,season,ep` and searches by title, and the entire design
  collapses into fuzzy Swedish-title matching.
- `<limits max="100">` is what the feed's 100-item cap honours.

Everything the document advertises is honoured by the route, and a test reads
`supportedParams` out of the document and exercises each name it finds, so the
two cannot drift apart again.

**No request may produce an HTTP 500.** A 500 can make Sonarr disable the
indexer; an empty channel just means "nothing found this search".

The service checks no API key on any of these routes. Sonarr's form requires
one to be filled in; any placeholder satisfies it.

### SABnzbd — [`api/sab.py`](../src/svtplay_arr/api/sab.py)

SABnzbd is a usenet download client with an HTTP API keyed on `?mode=`. Sonarr
drives it to queue downloads and to learn how they went.

**What is implemented:**

| Request | Behaviour |
| --- | --- |
| `mode=version` | Reports `4.3.0`. |
| `mode=get_config` | `misc.complete_dir` plus a `categories` list. |
| `POST mode=addfile` | Parse the `.nzb`, create a job. |
| `mode=queue` | Active jobs with real percentages and byte counts. |
| `mode=history` | Terminal jobs with `storage` and `fail_message`. |
| `mode=queue&name=delete&value=...` | Terminate running jobs. |
| `mode=history&name=delete&value=...` | Remove finished rows. |
| Anything else | `{"status": false, "error": "unsupported mode ..."}` |

`value` accepts one id, a comma-separated list, or the literal `all` — all
three are legal SABnzbd and all three work here.

**Removal is not a mode.** There is no `mode=delete` in SABnzbd; it is a
sub-action of `queue` and `history`, keyed on `name`. Declaring `name` as a
parameter is what makes it reachable at all — without it, Sonarr's delete fell
through to the listing branch and answered with the queue while deleting
nothing.

Deletes are filtered to jobs that exist and are on the correct side of the
queue/history split, so a delete can neither invent a job nor flip an
already-`Completed` one to `Failed` after its file has landed in `completed/`
and possibly been imported.

**Why SABnzbd emulation rather than a blackhole client**, which would have been
far less work — three concrete reasons, each with a matching requirement in the
code:

- A genuine percentage in Sonarr's Activity tab during a multi-GB download,
  which means the `.nzb`'s declared size has to survive `addfile` intact.
- Working failure reporting, so a failed grab re-searches instead of stalling
  in a queue slot that never moves. That needs `fail_message` in history.
- **Remote path mapping.** Sonarr keys remote path mappings on the download
  client's *host*. A blackhole client has no host, so no mapping can ever apply
  to one, and `completed/` would have to sit at an identical path on both
  sides. A SAB client reports a hostname, so the existing pattern applies
  unchanged.

`get_config` must return a `categories` list or the download client is
**unsaveable**: Sonarr derives `OutputRootFolders` from the configured
category's entry and fails validation without it. The `dir` is empty on
purpose — an empty relative dir means the category's full path *is*
`complete_dir`, which is where the worker publishes. It must not end in `*`
either; Sonarr reads a trailing `*` as "job folders disabled" and fails
validation for that too.

**Every route is `async def`.** `JobStore` serialises access to one shared
`sqlite3.Connection` behind a blocking `threading.Lock`; FastAPI runs non-async
routes in a threadpool, and a threadpool thread holding that lock would stall
the event loop — and with it the download worker — for as long as it held it.

## The atomic publish

[`src/svtplay_arr/worker.py`](../src/svtplay_arr/worker.py). The single most
consequential twenty lines in the project.

Sonarr's completed-download handling imports whatever it finds in
`completed/`. A partial file appearing there is a permanent, corrupt library
entry. So publication happens only after the downloader has returned
successfully, and only via `Path.rename`, which is atomic within one
filesystem: the file appears whole or it does not appear.

The sequence:

1. `completed/` is created if needed and chmodded to `775` explicitly —
   `mkdir`'s own `mode` argument is masked by the process umask, so it is not
   trusted to have applied it.
2. The video is confirmed to exist in staging as `<stem>.mkv`. If it does not,
   the job fails.
3. **Sidecars move first.** Subtitles and anything else in staging whose name
   starts with `<stem>.` is chmodded to `664` and renamed into `completed/`.
   Anything not matching the stem is left behind and swept up with the staging
   directory — it is not part of this release.
4. **The video is renamed last.** That single rename is the moment the job
   becomes visible and importable to Sonarr as a whole.
5. If anything fails partway, sidecars already moved are unlinked, so
   `completed/` never holds orphaned, importable-looking leftovers for a video
   that never arrived.

**If `incomplete/` and `completed/` are on different filesystems, `rename`
silently degrades to copy-then-delete and this entire guarantee is lost.**
Nothing detects that after the fact. `Settings.dirs_share_filesystem()`, surfaced
as `same_filesystem` on `/health`, is the only check for it.

### Crash recovery

`sweep_incomplete()` runs at startup and does two things:

- **Deletes everything in `incomplete/`**, so a partial left by a crash can
  never be mistaken for a live download. This is why `completed/` must not live
  inside `incomplete/`, and why the service refuses to start if it does.
- **Reconciles the store.** A job that was mid-download when the process died
  is still `Downloading`, and the poll loop only ever dispatches `Queued` jobs
  — so without this it would sit in Sonarr's Activity tab at its last reported
  percentage forever, never retried and never failed, with no error shown
  anywhere. Marking it `Failed` is the whole recovery path: a failed job with a
  `fail_message` is exactly what `autoRedownloadFailed` acts on, so Sonarr
  re-searches by itself. The download restarts from zero; `svtplay-dl` has no
  resume.

The worker also re-reads the job's status after acquiring the semaphore and
again after the download returns, so an out-of-band change — Sonarr deleting
the job from its queue mid-download — cannot be overwritten by an
unconditional `complete()`.

## `/health` and the status strip

[`src/svtplay_arr/app.py`](../src/svtplay_arr/app.py).

`/health` reports the filesystem check, whether the worker task is alive, the
active job count, and the mapping table's state. It never returns a 500: a
store error is reported as a degraded-but-200 response, because this is
Sonarr-facing infrastructure too.

The configuration page's status strip and `/health` are computed by **one
function**, `compute_health()`, which both call and render verbatim. This
project has repeatedly been bitten by two places computing the same fact and
drifting apart — it is the most common defect class in its history — and a
status strip that disagreed with `/health` would be worse than no strip at all,
because the operator would trust the one in front of them.

## The configuration page

[`src/svtplay_arr/api/config_ui.py`](../src/svtplay_arr/api/config_ui.py) plus
Jinja2 templates under `src/svtplay_arr/templates/`.

Server-rendered HTML mounted at `/config`. It contains no matching logic and no
SVT knowledge — it calls the same `SvtClient` and `SonarrClient` that
`discovery.py` does, which is the seam that guarantees a UI change cannot alter
what gets grabbed. The Find mappings sweep is the one route that writes without
a per-row confirmation, and it may write only what
`discovery.corroborated_match` approved; that gate lives in `discovery.py`,
not here.

Four server-rendered views behind a nav bar, listed once in
`config_ui.VIEWS`. `/config` still serves the entry point it always did — it
is documented, deployed, and the published SSO resource points at it — but
what it serves is now **Status**, not the settings form. An operator opens
this page to ask "is it working" far more often than to change a setting,
and a setting needs a restart before it does anything.

Routes:

```
GET  /config                            Status: is it working?
GET  /config/mappings                   Mappings: the table, add/remove, sweep
GET  /config/settings                   Settings: the form
POST /config/settings                   save settings
GET  /config/mappings/new               "which show?" form
POST /config/mappings/search            SVT hits beside Sonarr series
POST /config/mappings                   create one mapping
POST /config/mappings/{tvdb_id}/delete  remove one
POST /config/mappings/{tvdb_id}/check   live-check one mapping's slug
POST /config/mappings/discover          sweep Sonarr for unmapped series
```

`POST /config/mappings/discover` is the Find mappings sweep. It parses
`expected_mtime`, loads mappings.yaml (refusing to sweep at all if it will not
parse — without knowing what is already mapped it would re-search the library
and could append a duplicate on top of a file it could not read), runs
`discovery.sweep_for_mappings` (passing the `air_date_tolerance_days` the
service booted with, so the sweep corroborates at the window the resolver will
later match at), and writes the corroborated rows in **one** atomic
`add_mappings` call. The sweep itself writes nothing, so a Sonarr or SVT outage
part-way through leaves no partial file. Bounded at 4 concurrent **series**,
200 series per run and 600 SVT requests per run; whichever limit bites is
reported on the page, not silently applied — a partial sweep reported as a
complete one is the failure mode that matters here. The concurrency bound is on
series rather than on requests because `asyncio.gather` starts every series at
once: a request-level semaphore is FIFO, so each series advanced one request per
round, the budget was spent breadth-first and a real-sized run finished nothing.
Holding it per series makes the run depth-first. Rows land marked
`source: auto`; a suggestion accepted by hand goes through
`POST /config/mappings` like any other and stays `manual`.

The rules it inherits, all of them pinned by tests:

- **Every function works with JavaScript disabled.** There is one inline
  `<script>` in `base.html`, and it is progressive enhancement only: the
  per-mapping Check control is a plain form POST whose response is the whole
  page re-rendered, and the script only swaps that for a `fetch` that patches
  one row. The mapping filter box is the reverse — the server never renders it,
  and the script creates it, because a filter that cannot filter is worse than
  no filter. The API key's reveal control is pure CSS (a nameless checkbox and
  a `:checked ~` rule) and stays that way, because it *is* the control rather
  than an enhancement on top of one.
- **No build step, no bundler, no CDN, no `<script src>`.** The deploy path is
  `git pull`, `uv sync`, restart, with no node anywhere.
- **Never an HTTP 500** where a rendered error will do.
- **The page cannot restart the service**, alter the worker, or touch the
  download pipeline.
- Server-supplied strings written into the DOM by script go through
  `textContent`, never `innerHTML`, and the response is validated before it is
  painted — an SSO JSON 401 or a proxy error body parses perfectly well
  otherwise.

## The SVT client

[`src/svtplay_arr/svt/client.py`](../src/svtplay_arr/svt/client.py). Three
surfaces, all reverse-engineered, none of them documented or stable.

- **Contento GraphQL** (`api.svt.se/contento/graphql`) for series search.
- **The show page HTML** (`svtplay.se/{slug}`) for the episode list, parsed by
  `svt/parser.py`.
- **The video endpoint** (`api.svt.se/video/{svt_id}`) plus the HLS master
  manifest it points at, for quality and exact duration.

Three quirks are worth knowing because they explain code that otherwise looks
paranoid:

**The CDN returns cached responses across different query strings.** Two
different GraphQL queries were observed coming back with the same body. A
structural check does not catch this — the swapped body is perfectly
well-formed JSON for *some* query. So every request carries a cache-buster
*and* a per-request field alias (`q<nonce>: search(...)`), and the response's
`data` block must echo that exact alias before anything in it is trusted.

**The show page's `__NEXT_DATA__` is empty of content.** The episode list lives
in an HTML-escaped JSON payload elsewhere in the markup, which is why the
parser unescapes and scans rather than parsing something structured.

**Quality is not in the video endpoint.** Its `videoReferences` entries carry
only `format`, `url`, `resolve` and `redirect` — no resolution, no bitrate. The
quality ladder is in the HLS master playlist one of those entries points to.
The same video endpoint response does carry an exact `contentDuration`, which
is materially better than the show page's coarse "N min" subheading (observed
drifting up to ~19% off), so it is threaded through for size estimation.

## Testing

Every external boundary is behind an interface: the SVT client, the Sonarr
client, the downloader, the filesystem. The unit suite runs entirely offline
against fixtures recorded from real SVT responses on a known date, so **SVT API
drift surfaces as a fixture mismatch rather than as a production mystery**.

Two rules that shaped a lot of the test code:

- **Fixtures are ground truth, not the code.** When the parser and a fixture
  disagree, the fixture wins and the parser gets fixed.
- **A synchronous fake cannot test an asynchronous protocol.** The worker is
  long-running and Sonarr polls `mode=queue` *during* the download, so a fake
  that completed instantly would make every queue test pass while proving
  nothing. `FakeDownloader` models progress over simulated time and a test
  asserts intermediate states are observable.

One opt-in integration test hits the real SVT API. It requires a Swedish IP and
is excluded from CI.

See [CONTRIBUTING.md](../CONTRIBUTING.md) for how to run all of this, and for
the testing culture this project expects of a change.
